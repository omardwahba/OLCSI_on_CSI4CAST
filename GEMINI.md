# CSI-4CAST Context Guide

## Project Overview
**CSI-4CAST** is a comprehensive framework for generating and evaluating Channel State Information (CSI) prediction models using 3GPP TR 38.901 channel models. It supports large-scale dataset generation, deep learning model training (using PyTorch Lightning), and extensive robustness/generalization testing.

### Key Components
*   **`src/data`**: **Data Generation Module**. Uses the [Sionna](https://github.com/NVlabs/sionna) library to simulate realistic channel responses (time-domain/frequency-domain) under various mobility and delay spread conditions.
*   **`src/cp`**: **Channel Prediction Module**. The core training framework.
    *   **Entry Point**: `src/cp/main.py`
    *   **Models**: Defined in `src/cp/models/` (Base class: `BaseCSIModel`).
    *   **Config**: Managed by `src/cp/config/config.py`.
*   **`src/noise`**: **Noise Module**. Handles realistic noise modeling (Phase noise, Burst noise, etc.) and calibration.
*   **`src/testing`**: **Evaluation Module**. Metrics (NMSE, SE), computational overhead profiling, and visualization tools.
*   **`scripts/`**: SLURM templates for HPC execution (Phoenix cluster).
*   **`z_artifacts/`**: Designated output directory for datasets, model checkpoints, logs, and visualization results.

## Building and Running

### 1. Environment Setup
The project uses `mamba` (or `conda`) for environment management.
```bash
mamba env create -f env.yml
mamba activate csi-4cast-env
```

### 2. Data Generation
Generate CSI datasets before training. The script `src/data/generator.py` handles this.
*   **Training Data**: `python3 -m src.data.generator --is_train`
*   **Test Data (Regular)**: `python3 -m src.data.generator`
*   **Test Data (Generalization)**: `python3 -m src.data.generator --is_gen`
*   **Debug Mode** (Minimal data): Add `--debug` flag.

*After generation, compute normalization statistics:*
```bash
python3 -m src.utils.norm_utils
```

### 3. Model Training
Training is driven by `src/cp/main.py` using configuration files generated by `src/cp/config/config.py`.

**Step A: Generate Config**
```bash
# Example
python3 -m src.cp.config.config --model rnn --output-dir z_artifacts/config/cp/rnn/ --is_U2D False --config-file yaml
```

**Step B: Train**
```bash
python3 -m src.cp.main --hparams_csi_pred z_artifacts/config/cp/rnn/tdd_rnn.yaml
```
*   **Outputs**: Checkpoints and TensorBoard logs in `z_artifacts/outputs/`.
*   **Monitoring**: `tensorboard --logdir z_artifacts/outputs/[path]/tb_logs`.

### 4. Testing & Evaluation
*   **Performance**: `python3 -m src.testing.prediction_performance.main --model [model_name]`
*   **Overhead**: `python3 -m src.testing.computational_overhead.main`
*   **Analysis**: `python3 -m src.testing.results.main` (Aggregates results)
*   **Visualization**: `python3 -m src.testing.vis.main` (Generates plots in `z_artifacts/outputs/testing/vis/`)

## Development Conventions

*   **Code Style**: The project uses `ruff` for linting and formatting.
    *   Configuration: `pyproject.toml`
    *   Run: `ruff check .` / `ruff format .`
*   **Module Invocation**: Always run scripts as modules from the root directory (e.g., `python3 -m src.module.script`).
*   **Path Management**: Use `src/utils/dirs.py` or relative paths carefully. Artifacts should strictly go into `z_artifacts/`.
*   **HPC Compatibility**: Scripts in `scripts/` are designed for SLURM. Ensure any new heavy processing tasks have corresponding SLURM templates if intended for cluster use.

### Phase Two — Model creation (CNN + MLP) 🧱

**Goal:** Implement a compact CNN model that balances good performance with a small number of parameters. Model architecture (high-level):
- Conv2D(32, kernel=3) → BatchNorm -> MaxPool2D
- Conv2D(64, kernel=3) → MaxPool2D 
- Conv2D(128, kernel=3) → MaxPool2D → Flatten
- Two-stage MLP that reshapes the flattened vector into the required output image shape:
  - MLP width constructor: reshape to [batch, antennas?, time?, width=subcarriers]
  - MLP height constructor: reshape to final [batch, antennas?, pred_len (time), subcarriers]

**Detailed steps:**
1. Design model class inheriting from `BaseCSIModel` (`src/cp/models/common/base.py`). Ensure consistent `is_separate_antennas` semantics.
   - Suggested path: `src/cp/models/cnn_online.py` and a registry entry if needed.
2. Implement `forward()` to accept dataloader-output shapes (either separate-antennas real format `[B*T, hist_len, subcarriers*2]` or gather antennas complex format `[B, antennas, hist_len, subcarriers]`).
   - If `is_separate_antennas=True` (recommended for parameter efficiency), the input is real; convert tensors to suitable shape for 2D-conv: e.g., view `[batch, 1, hist_len, subcarriers*?]` or `[batch, channels, H, W]`.
3. Implement the two-stage MLP decoder:
   - After flattening, have a small linear block that outputs `batch * subcarriers` then reshape and another linear block to output `batch * pred_len * subcarriers` with final reshape to match `H_pred` format.
4. Add model registration and config support:
   - Update `src/cp/config/config.py` ModelConfig `params` to include architectural params (filters, kernel sizes, hidden dims).
   - Provide an example YAML config or CLI example to generate config via `src/cp/config/config.py`.
5. Add unit tests / smoke tests:
   - Small unit test in `src/testing/prediction_performance/test_unit.py` or a new test that instantiates the model and runs a forward pass with a small debug sample (use debug dataset in `z_artifacts/data/.../debug` and `BATCH_SIZE_DEBUG`).
6. Run a tiny end-to-end debug run:
   - Use debug dataset (`--debug`) and `DataConfig.batch_size=2`, check that forward pass runs and output shape matches target shape.

**Files to modify/create:**
- Create: `src/cp/models/cnn_online.py` (model implementation)
- Optionally update: `src/cp/models/__init__.py` (to expose model), `src/cp/config/config.py` (ModelConfig example), tests in `src/testing/`.

**Notes & suggestions:**

### Phase Three — Online training & evaluation ⚡

**Goal:** Train the model in an online fashion (update every batch, batch size 1), ensure FDD evaluation, and report both prediction performance (NMSE, SE) and computational metrics (FLOPs, per-sample training time, per-sample inference time).

**Core artifact:** Implement **all Phase 3 code in a single script**: `online_csi/online_test.py` (CLI entry point). This script will (1) run online training, (2) measure FLOPs and timings, and (3) evaluate performance on the regular FDD test set. The script needs to use the existing testing script provided, so make sure output data is as expected.

**Design & responsibilities of `online_test.py`:**
- CLI arguments (examples):
  - `--model NAME` (e.g., `RNN` or your custom `CNN`), `--scenario FDD`, `--batch_size 2`, `--num_updates 100` (number of online batches to process), `--device cpu|cuda`, `--is_separate_antennas` / `--gather_antennas`, `--compute_flops` (bool), `--measure_time` (bool), `--evaluate` (bool), `--outdir` (optional).
- Core functions:
  1. run_online_training(model, datamodule, optimizer, criterion, num_updates, device, warmup=5)
     - Iterates `num_updates` batches from `dm.train_dataloader()` (no epoch loops required). For each batch:
       - Record walltime for the full update step: forward → loss → backward → optimizer.step() → optimizer.zero_grad().
       - Compute per-sample training time = elapsed_time / num_samples_in_batch (use `hist.shape[0]` after collation because separate-antennas increases effective batch size).
       - Collect statistics (mean, std, median) across updates, excluding `warmup` steps.
  2. measure_inference_per_sample(model, device, n_iters=50)
     - Use `src/testing/computational_overhead.utils.measure_inference_time_stats` on a single-sample input (batch_size=1) to get mean/std/min/max.
  3. compute_flops_per_sample(model, device)
     - Reuse `src/testing/computational_overhead.utils.count_flops` or `compute_all_metrics` with `batch_size=1` to get FLOPs (forward pass) and inference stats. Document that DeepSpeed profiler counts forward FLOPs; training FLOPs are not automatically provided and would need separate estimation.
  4. evaluate_model_on_testset(model, dir_data, is_U2D=True, device, out_csv)
     - Reuse `src/testing/prediction_performance.test_unit` to evaluate NMSE/SE over the regular FDD test combinations (iterate over `LIST_CHANNEL_MODEL`, `LIST_DELAY_SPREAD`, `LIST_MIN_SPEED_TEST`). Save aggregated results to `z_artifacts/outputs/testing/online_test/<timestamp>/results.csv`.
- Output artifacts:
  - `results.csv` with performance metrics (NMSE, SE, etc.) per combination
  - `comp_metrics.json` or CSV with computational metrics (FLOPs, inference ms, training ms per sample, parameter counts)
  - Optional model checkpoint (if you want to resume or re-evaluate) saved to `z_artifacts/weights/online_test/<timestamp>/`

**Important implementation notes:**
- FDD enforcement: Script must set `DataConfig.is_U2D=True` for training and evaluation, and use FDD targets (`H_D_pred.pt`). Also set `DataConfig.shuffle=False` to preserve online ordering.
- FLOPs & inference timing: We can reuse `src/testing/computational_overhead/utils.py` (`count_flops`, `measure_inference_time_stats`, `compute_all_metrics`) directly; call with `batch_size=1` to get per-sample FLOPs and inference times.
- Training time per sample: The repository's timing utilities measure forward-pass time and inference timings; they do not include optimizer/backward/step durations. We will implement training time measurement inside `run_online_training()` by timing the full update step and dividing elapsed time by the *actual* number of samples in the batch (i.e., `hist.shape[0]`) to obtain the per-CSI-image training time (one CSI image = one antenna sample in separate-antennas mode).
- Separate vs gather antennas: If `is_separate_antennas=True`, the collated `hist` tensor will have shape `[batch_effective, hist_len, subcarriers*2]` and the effective number of CSI images per batch is `hist.shape[0]`. If `is_separate_antennas=False`, the per-sample definition should be clarified (one CSI image might refer to one full multi-antenna sample). The script will document and accept a `--per_sample_mode` flag if needed.
- Warmup & stability: Exclude the first few updates from timing statistics to avoid CUDA kernel initialization and caching effects (e.g., `warmup=5`). Repeat measurement over multiple updates for stable mean/std estimates.
- Device syncing: Always `torch.cuda.synchronize()` before stopping timers when using CUDA for accurate timing.

**Integration with existing evaluation pipeline:**
- Use `test_unit()` to evaluate model performance on the regular FDD testset (it handles normalization, denormalization, noise application, and metrics aggregation). For online_test we will call `test_unit()` with `scenario='FDD'`, `is_gen=False`, `is_U2D=True`.

**Example CLI usages:**
- Quick debug (small number of updates, CPU):
  - `python -m src.testing.online_test --model RNN --scenario FDD --batch_size 2 --num_updates 20 --device cpu --compute_flops --measure_time --evaluate`
- GPU run with measurements:
  - `python -m src.testing.online_test --model RNN --scenario FDD --batch_size 2 --num_updates 200 --device cuda --compute_flops --measure_time --evaluate`
